# 12 — النشر والتشغيل (Vercel + Neon)

الإنتاج يعمل على ثنائية واحدة موثّقة: **Vercel** (مشروع `tadmora` — دوال
serverless في إقليم `fra1`/فرانكفورت، الرابط الإنتاجي
**https://tadmora.vercel.app**) + **Neon PostgreSQL** (مشروع `tadmora-production`
في `aws-eu-central-1` — فرانكفورت أيضًا، بجوار الدوال). النشر يتم عبر
**Vercel CLI** من جذر المستودع، و`vercel.json` هو مخطط النشر الوحيد. لا توجد
خطوات نشر داخل CI (يبني ويفحص فقط)، وربط GitHub التلقائي غير مفعل بعد —
الخطوة اليدوية المعروفة موثّقة في قسم النشر أدناه.

## المتطلبات

1. حساب Vercel + ‏CLI (يعمل عبر `npx vercel` — لا تثبيت دائم مطلوب) ومشروع
   باسم `tadmora` مربوط بالمستودع (`npx vercel link` أول مرة).
2. مشروع Neon PostgreSQL: `tadmora-production` — ‏PG 16، إقليم
   `aws-eu-central-1` (فرانكفورت).
3. سرّا JWT مختلفان + سرّ خدمة داخلي واحد (القسم «متغيرات البيئة»).

## قاعدة البيانات — Neon: المشروع والفروع وسلسلتا الاتصال

مشروع Neon الواحد يعرّض **سلسلتي اتصال** لكل فرع، والتمييز بينهما جوهري:

| السلسلة | الشكل | استخدامها |
|---|---|---|
| **المجمّعة (pooler)** | المضيف ينتهي بـ`-pooler` (عبر PgBouncer) | `DATABASE_URL` في بيئة Vercel — وقت تشغيل الدوال: كل استدعاء دالة اتصال قصير العمر، و`pgbouncer=true&connection_limit=1` يمنع الدوال من حجز اتصالات مخصصة |
| **المباشرة (direct)** | المضيف بلا `-pooler` | أعمال المشغّل من `backend/`: الترحيلات والبذرة والنسخ/الاستعادة — لا تمر عبر PgBouncer |

- **فرع الإنتاج** هو ما تشير إليه `DATABASE_URL` في بيئة Vercel.
- فرع **`development`** المعزول في نفس المشروع للتطوير والتجارب: بيانات
  منفصلة وسلسلتا اتصال خاصتان به — استعمله لأي تجربة استعادة أو فحص مخطط
  قبل الإنتاج (لا تجرّب على فرع الإنتاج أبدًا).
- المنطقة فرانكفورت في الطرفين عمدًا: الدوال في `fra1` بجوار قاعدة
  `aws-eu-central-1` لتقليل زمن الاستعلام.

## الترحيلات والبذرة — من `backend/` (فعل مشغّل صريح)

بناء Vercel **لا يلمس قاعدة البيانات** (القسم التالي)، فالترحيل والبذرة
خطوة مشغّل واعية تُنفَّذ من `backend/` عبر السلسلة المباشرة:

```bash
cd backend
DATABASE_URL='<سلسلة الاتصال المباشر من لوحة Neon>' node scripts/migrate-deploy.mjs
DATABASE_URL='<السلسلة نفسها>' npm run prisma:seed   # أول إقلاع فقط — انظر العقد
```

- `scripts/migrate-deploy.mjs` يطبّق `prisma migrate deploy` بمسار مرن:
  يفضّل `DIRECT_DATABASE_URL` إن ضبطته، وإلا اشتقّ المباشر بنفسه بحذف
  `-pooler` من اسم المضيف وحذف معاملات `pgbouncer`/`connection_limit`، مع
  إيقاظ Neon البارد وإعادة المحاولة — التفصيل في [07-database](07-database.md).
- **عقد البذرة (r183)**: البذرة تعمل كإقلاع أولي تلقائي على قاعدة **فارغة**
  فقط (لا مستخدمين)؛ أما **القاعدة المؤسَّسة فتُتخطى بالكامل** (صفر كتابات:
  لا تصفير كلمات مرور ولا مساس بإعدادات أو سجلات — النشر العادي لا يعيد ضبط
  بيانات اعتماد أبدًا). الاستثناء الموثّق: حسابات الاختبار `@test.ly` (R320
  §C) يضمنها البذر دائمًا. أما إعادة ضبط بيانات العرض الواعية ففعل مشغّل
  صريح ومعزول:
  `TADMORA_SEED_FORCE=1 npm run db:seed:force` — وحتى في مسار FORCE يبقى
  العقد: التقدم التعليمي المُدار من المستخدمين (درجات/إتقان/مشاهدات/مستويات
  مهارات) **لا يُرجَع أبدًا** (upserts إنشاء-فقط) — انظر رأس
  `backend/prisma/seed.ts` وعقد الاختبار في
  `backend/tests/integration/seed-idempotency.test.ts`.

## خريطة النشر — ماذا يعدّ `vercel.json` (و`.vercelignore`)

| البند | القيمة | المعنى التشغيلي |
|---|---|---|
| `framework` / `outputDirectory` | `vite` / `frontend/dist` | الواجهة أصول ثابتة تقدّمها طبقة Vercel الثابتة |
| `functions` | `api/index.ts` — دالة واحدة، `maxDuration: 60` | تطبيق Express كاملًا هو المعالج، بميزانية 60 ثانية للاستدعاء |
| `rewrites` | `/api/(.*)` → `/api`، والباقي → `/index.html` | كل واجهات `/api/v1/*` تمر عبر الدالة، وكل مسار آخر يسقط على SPA fallback |
| `headers` | CSP ببصمات `sha256-` مثبتة + ‏HSTS/`X-Frame-Options`/`nosniff`/`Referrer-Policy`/COOP… | ترويسات الأمان على كل الاستجابات — غياب بصمات CSP يعني خللًا لا تحذيرًا (قرار D7) |
| `crons` | `0 3 * * *` → ‏`GET /api/v1/jobs/daily` | الوظائف اليومية (مزامنة الحقائق + تقليم سجلات الدخول) — لا عملية طويلة العمر في serverless |
| `installCommand` / `buildCommand` | `npm ci` / توليد Prisma → بناء الواجهة → بناء الخلفية → حارس وجود `backend/dist/app.js` | بناء **بلا قاعدة بيانات** عمدًا: الترحيلات فعل مشغّل (القسم السابق)، لذا لا يحتاج البناء قاعدة حية — ولهذا السبب نفسه يبني CI كل جهة منفصلة بلا ترحيلات |

- **الدالة نفسها** (`api/index.ts`): تطبيق Express (‏`backend/src/app.ts` →
  `createApp()`) هو معالج الدالة مباشرة — نفس واجهات `/api/v1/*` حرفيًا.
  مدخل العملية الطويلة (`backend/src/index.ts` — استماع + مجدول داخل
  العملية) **لا يُستخدم** على Vercel: الوظائف المجدولة تركب cron المنصّة،
  والمصادقة عبر `Authorization: Bearer <CRON_SECRET>` (القسم التالي).
- **`.vercelignore`**: سياق الرفع هو **منصة الويب فقط** — backend + frontend +
  shared + api + ملفات أداة البناء. كل ما عدا ذلك (تطبيق الجوال في `apps/`،
  التوثيق في `docs/`، المواصفات في `specs/`، سجلات الهندسة، أدوات الفحص
  المحلية) يبني ويسافر عبر خطوطه الخاصة ولا يدخل حزمة الرفع.

## متغيرات البيئة (مشروع Vercel — بيئة Production)

**الإلزامية:**

| المتغير | القيمة/السلوك |
|---|---|
| `DATABASE_URL` | سلسلة Neon **المجمّعة (pooler)** لفرع الإنتاج، بالشكل: `postgresql://USER:PASS@HOST-pooler.REGION.aws.neon.tech/DB?sslmode=require&pgbouncer=true&connection_limit=1` |
| `JWT_ACCESS_SECRET` | 64 بايت hex عشوائية (الحد الأدنى في `env.ts` 32 محرفًا — لا تُقلّص) |
| `JWT_REFRESH_SECRET` | 64 بايت hex **مختلفة** |
| `INTERNAL_SERVICE_TOKEN` | سرّ الخدمة الداخلي (16 محرفًا على الأقل) — يحرس مسارات الخدمة الداخلية و`GET /api/v1/jobs/daily`، ويُقارن بتوقيت ثابت (SHA-256 + timingSafeEqual) |
| `CRON_SECRET` | **نفس قيمة `INTERNAL_SERVICE_TOKEN` حرفيًا** (سرّ واحد بشكلَي نقل): cron المنصّة يرسل `Authorization: Bearer <CRON_SECRET>` والدالة تقارنه بـ`INTERNAL_SERVICE_TOKEN`؛ بلا ضبطهما يُرفض الطلب فشلًا مغلقًا |

توليد سرّ عشوائي:

```bash
node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
```

**الاختيارية** (السلوك الكامل في [06-configuration](06-configuration.md)):

| المتغير | الافتراضي | ملاحظات |
|---|---|---|
| `CORS_ORIGINS` | `https://tadmora.vercel.app,http://localhost:5173` | قائمة سماح مفصولة بفواصل؛ ضبطها **يستبدل** الافتراضي كليًا (لا يلحقه) — أضف نطاق الإنتاج ضمنها |
| `STORAGE_DRIVER` | `local` | في الإنتاج اضبط `postgres` (دوام BYTEA داخل قاعدة Neon — بلا متغيرات إضافية، يستعمل `DATABASE_URL` نفسها) أو `s3` + متغيرات `S3_*` الأربعة |
| `DIRECT_DATABASE_URL` | مشتقّة تلقائيًا | الاتصال المباشر للترحيلات؛ لا حاجة لها ما دام الاشتقاق (حذف `-pooler`) صحيحًا |
| `APP_ORIGIN` | غير مضبوط | أصل روابط البريد — مثال: `https://tadmora.vercel.app` |
| `AI_PROVIDER` + `AI_API_KEY` + `AI_MODEL` (+ `AI_BASE_URL`) | `local` | المحرّك المحلي الحتمي افتراضيًا (بلا استدعاءات خارجية)؛ لنموذج حقيقي: `AI_PROVIDER=openai` مع أي خدمة متوافقة (الخطوات أدناه) |
| `MAIL_PROVIDER` + `MAIL_API_KEY` + `MAIL_FROM` | `none` | بلا بريد افتراضيًا — المسار الموثّق هو رابط إعادة التعيين اليدوي من المسجّل العام |
| `TADMORA_TEST_ACCOUNTS` | غير مضبوط | اضبط `1` لضمان حسابات `@test.ly` عند كل إقلاع خلفية (الحزام الذاتي الشافي فوق البذرة) |

> كل هذه المتغيرات تُدار من إعدادات مشروع Vercel (Settings → Environment
> Variables) — لا تُوضع أسرار حقيقية في أي ملف متتبَّع بالمستودع أبدًا.

## النشر — Vercel CLI من جذر المستودع

```bash
npm ci                                 # تثبيت نظيف (نفس installCommand)
npx vercel deploy --prod --regions fra1
```

- `--regions fra1` يثبّت الدوال في فرانكفورت بجوار قاعدة Neon.
- بعد النشر: شغّل فحص الدخان (القسم أدناه).

> **ربط GitHub التلقائي — الخطوة اليدوية المعروفة:** النشر اليوم يتم عبر
> CLI فقط كما أعلاه. تفعيل النشر التلقائي عند كل دفع إلى `main` يتطلب إضافة
> اتصال تسجيل دخول GitHub إلى حساب Vercel (إعدادات الحساب → Git) — خطوة
> يدوية واحدة عند المالك لم تُنفَّذ بعد؛ حتى تُنفَّذ، كل نشر فعل صريح عبر
> الأمر أعلاه.

## تقوية الإنتاج بعد البذرة (تسلسل المشغّل — مرة واحدة)

البذرة تنشئ مالكًا تجريبيًا بكلمة مرور معلَنة (مستودع عام = كلمة منشورة) —
**لا يُترك الإنتاج عليها**. التسلسل المفوَّض بعد أول بذرة (كلا السكربتَين
يرفض العمل على الإنتاج بلا `--yes`، ومن يملك `DATABASE_URL` هو التفويض):

**1) حساب مالك بهوية المشغّل — `provision-owner.mjs`** (r187): ينشئ حساب
OWNER واحدًا عالميًا ببريد المشغّل المتحقّق، يسجّل صف `OWNER_PROVISION` في
سجل التدقيق داخل نفس المعاملة، ويطبع السرّ **مرة واحدة** بين علامات واضحة
إن لم تمرّر `--password-env` (كلمة المرور عبر متغير البيئة لا تُطبع أبدًا):

```bash
cd backend
DATABASE_URL='<مباشر>' node scripts/provision-owner.mjs \
  --email <بريدك-المتحقق> --yes --suspend-demo-owner
```

`--suspend-demo-owner` يعلّق المالك التجريبي (‏`isActive=false` + إبطال
جلساته) **بعد** إنشاء الحساب الجديد وبنفس المعاملة — لا تنتهي المنصة بصفر
مالكين نشطين أبدًا. لا مسار عام يمنح OWNER: لا تصعيد صامت لهوية قائمة
(بريد موجود بدور آخر → رفض قاطع؛ بريد مالك قائم → التوجيه للتدوير أدناه).

**2) تدوير كلمات المرور — `rotate-demo-passwords.mjs`** (r166c): المسار
المفوَّض لتدوير كلمة مرور أي حساب بيد من يملك `DATABASE_URL` — وهو **مسار
استعادة حساب المالك عند فقدان كلمته** (لا يوجد إعادة تعيين داخل التطبيق
للمالك):

```bash
cd backend
export NEW_PASSWORD="$(openssl rand -base64 24)"    # كلمة قوية — لا تُمرَّر وسيطًا أبدًا
DATABASE_URL='<مباشر>' node scripts/rotate-demo-passwords.mjs \
  --email owner@test.ly --new-password-env NEW_PASSWORD --dry-run   # معاينة (قراءة فقط)
DATABASE_URL='<مباشر>' node scripts/rotate-demo-passwords.mjs \
  --email owner@test.ly --new-password-env NEW_PASSWORD --yes       # التنفيذ
```

دلالات التدوير تطابق `changePassword` في التطبيق (`auth.service.ts`): تجزئة
argon2id **بنفس معاملات `src/lib/password.ts`** (اختبار وحدة يثبّت التطابق
حرفيًا فلا يتباعد المصدران)، وتحديث **ذرّي واحد** يرفع `tokenVersion`
(إبطال كل الجلسات على كل الأجهزة) ويصفّر عدّاد محاولات الدخول الفاشلة.

> حسابات الاختبار الموثّقة (`@test.ly` / `12345678` — R320 §C) لحياة
> التطوير والعرض؛ إن رُقِّيت المنصة لاستخدام مؤسسي حقيقي دوّر كلماتها
> بالمسار نفسه.

## فحص الصحة والتحقق بعد النشر

- `GET /api/v1/health` → ‏200 JSON فيه `ok=true` و`dbLatencyMs` و`env` و
  `buildId` — يفحص `SELECT 1` بمهلة تمتص بداية Neon الباردة، و`BUILD_ID`
  ثابت نصي يساعد على تمييز النشر.
- سجلات التشغيل: لوحة Vercel (المشروع → Logs / تبويب الدالة) — pino JSON
  بمستوى info في الإنتاج مع حجب الأسرار.

## فحص الدخان بعد النشر — `npm run smoke`

سكربت `scripts/smoke-deploy.mjs` (r164-l) — Node خالص **بلا أي اعتماديات**
(يعمل على أي تثبيت node حتى بلا `node_modules`)، يفحص **نشرًا حيًا** ويعرض
جدول PASS/FAIL ويخرج برمز 0/1 — يصلح للتشغيل اليدوي بعد كل نشر أو لربطه
بأتمتة المالك:

```bash
BASE_URL=https://tadmora.vercel.app npm run smoke   # (وهذا هو الافتراضي أيضًا)
BASE_URL=https://<نطاقك> npm run smoke              # هدف مختلف عبر البيئة
SMOKE_EMAIL=<بريد> SMOKE_PASSWORD=<كلمة> npm run smoke   # + حلقة دخول كاملة
# فحص عزل المؤسستين — زوّد زوجًا ثانيًا لمستخدم مؤسسة أخرى:
SMOKE_EMAIL=<بريد أ> SMOKE_PASSWORD=<كلمة أ> \
SMOKE_EMAIL2=<بريد ب> SMOKE_PASSWORD2=<كلمة ب> npm run smoke
```

الفحوص الخمسة:

1. **الصحة**: `GET /api/v1/health` → ‏200 JSON فيه `ok=true` +
   `dbLatencyMs` (يُبلّغ عن قيمته) + `env` — بمهلة 90 ثانية وإعادة محاولة
   واحدة (امتصاص بداية Neon الباردة).
2. **الرئيسية**: `GET /` → ‏200 HTML فيه جذر تثبيت التطبيق (`id="root"`)
   **وترويسة CSP تحمل بصمات `sha256-`** (قرار D7 — غيابها يعني خللًا في
   ترويسات الأمان لا مجرد تحذير).
3. **صفحة الدخول**: `GET /auth` → ‏200 (مسار SPA fallback يخدم
   `index.html`).
4. **حلقة الدخول (اختيارية)**: تعمل فقط عند توفير `SMOKE_EMAIL` +
   `SMOKE_PASSWORD` **معًا** (المعرّف: البريد أو رقم القيد — كلاهما مقبول):
   `POST /api/v1/auth/login` → توكن وصول → `GET /api/v1/auth/me` بترويسة
   `Bearer` → مطابقة الدور بين الاستجابتين. لا تُطبع كلمة المرور ولا التوكن
   أبدًا، والبريد يظهر مقنّعًا (`a***@…`). تقديم متغير واحد فقط دون الآخر =
   فحص FAIL.
5. **عزل المؤسستين (r180، اختياري)**: يعمل فقط عند توفير
   `SMOKE_EMAIL`/`SMOKE_PASSWORD` **و** `SMOKE_EMAIL2`/`SMOKE_PASSWORD2`
   (مستخدم من مؤسسة أخرى): يسجّل الدخول بالمستخدمَين، يجلب تسجيلات كل منهما
   (`GET /enrollments/me`)، يتحقق أن مجموعتي الشعب **منفصلتان تمامًا**، ثم
   يطلب الأول شعبة مؤسسة الثاني (`GET /offerings/:id/full`) ويتحقق أن الرفض
   403/404 — أبدًا 200. (مثال جاهز: الطالبان التجريبيان `student@test.ly`
   و`student2@test.ly` — R320 §C.)

> قاعدة صدق: الفحص يلمس النشر الحي فقط ولا يُشغّل داخل CI أبدًا (وثيقة 11).
> إن ظهر فحص أحمر: راقب سجلات المشروع في لوحة Vercel ثم أعد المحاولة — حد
> المعدل على تسجيل الدخول (429) فحصٌ FAIL صادق يزول بعد دقيقة.

## التراجع عن إصدار معطوب

1. **الأسرع**: لوحة Vercel → ‏**Deployments** → النشر السابق السليم →
   **Rollback** (لا يلمس قاعدة البيانات — التراجع كودي فقط).
2. إن كان السبب ترحيلًا: الترحيلات **إضافية بالتصميم**؛ التراجع الكودي مع
   ترحيل رجوعي جديد مكتوب يدويًا فقط إن كان لا مفرّ — بقرار واعٍ ومُختبر
   على فرع `development` أولًا.
3. صحّح الكود وأعد النشر عبر CLI.

> التراجع أعلاه يعالج **الكود**. للتراجع في **البيانات** (استعادة قاعدة أو
> لحظة زمنية) انظر قسم «النسخ الاحتياطي والاستعادة» أدناه.

## النسخ الاحتياطي والاستعادة (دليل المالك — r164-l، السكربتات r166c)

> أدناه (`db:backup`/`db:restore`) مبنيان ومختبَران (حرّاسهما ووضعهما

### 1) ما تديره Neon تلقائيًا

- كل مشروع Neon يملك نسخًا احتياطية ذاتية حسب خطة المشروع، ومنها
  **الاستعادة النقطية الزمنية** (Point-in-Time Restore): من لوحة المشروع
  اختر لحظة زمنية واستعد إلى **فرع جديد** — الإنتاج نفسه لا يُلمس، وتحصل
  على قاعدة تحمل حالة تلك اللحظة.
- نافذة الاحتفاظ ومدى توفر PITR يختلفان **باختلاف خطة Neon** — تحقق من لوحة
  مشروعك (Project → Settings/Backups) ولا تفترض رقمًا من هنا.
- مسار العمل المقترح عند حادثة بيانات: استعِد إلى فرع جديد → تحقق منه
  (القائمة أدناه) → إن سليم وجّه `DATABASE_URL` في إعدادات مشروع Vercel
  إليه مؤقتًا (Settings → Environment Variables ثم Redeploy) — ثم صحّح
  الأصل بقرار واعٍ.

### 2) نسخة يدوية بقواعد «استراتيجية الرابطين»

الإنتاج يخدم الطلبات عبر **pooler** (`DATABASE_URL`)، وأعمال الصيانة
(الترحيلات والنسخ/الاستعادة) تحتاج الاتصال **المباشر** — هذا حرفيًا ترتيب
المرشحات في `backend/scripts/migrate-deploy.mjs`:

1. `DIRECT_DATABASE_URL` إن ضبطته في بيئة النشر (المفضلة).
2. وإلا اشتقّ المباشر بنفسك من سلسلة الـpooler: **احذف `-pooler` من اسم
   المضيف** واحذف معاملات `pgbouncer`/`connection_limit` (افتح سلسلة
   الاتصال من لوحة Neon → Connection Details → الاتصال المباشر نسخة جاهزة
   من ذلك).

> **r183 — طابق إصدار عميل pg مع الخادم:** استعادة بعميل 17.11 على خادم
> Neon 16.15 تفشل بخطأ `unrecognized configuration parameter
> "transaction_timeout"` (خاصية 17 لا يعرفها 16) — اِستخدم عميلًا بنفس
> الإصدار الأكبر للخادم (16.15↔16.15 هنا). الدرس كامل في مدخل 3 من سجل
> التجارب.

قالب النسخ (r166c: سكربت المشغّل فوق القالب الخام — على جهاز فيه أدوات
PostgreSQL):

```bash
# السلسلة من لوحة Neon (قيمة سرية — لا تضعها في ملف)
PG_DIRECT='<سلسلة الاتصال المباشر — بلا -pooler>'

# الطريقة الموصى بها: سكربت db:backup (scripts/db-backup.mjs) —
# يتحقق أن pg_dump مثبت (وإلا رسالة تثبيت ثنائية اللغة)، يقرأ
# المصدر من متغير البيئة بالاسم فقط، يقنّع السلسلة في كل المخرجات،
# ويطبع الحجم وبصمة sha256 للملف بعد النسخ:
npm run db:backup -- --url-env PG_DIRECT --label pre-migration
npm run db:backup -- --url-env PG_DIRECT --dry-run   # معاينة الأمر بلا تنفيذ

# الأمر الخام الذي يشغّله السكربت (قانون هذا الدليل نفسه —
# نسخة كاملة بصيغة custom قابلة للضغط والاستعادة الانتقائية):
pg_dump --format=custom --no-owner --no-privileges \
  --file="tadmora-$(date -u +%Y%m%dT%H%M%SZ).dump" "$PG_DIRECT"
```

قالب الاستعادة إلى قاعدة/فرع **تجريبي** (لا إلى الإنتاج مباشرة أبدًا — الفرع
الجديد في Neon يبدأ فارغًا فلا تحتاج `--clean`) — عبر سكربت `db:restore`
(scripts/db-restore.mjs) الذي يضيف حراسة صريحة:

- **هدف صريح إلزامي**: `--url-env <NAME>` — السكربت لا يقرأ `DATABASE_URL`
  ضمنيًا للهدف أبدًا (الاستعادة قرار واعٍ).
- **حارس الرفض الصارم**: إن طابق الهدفُ قاعدة الإنتاج (`DATABASE_URL`) رفض
  السكربت التنفيذ ما لم تُمرّر `--confirm-live-restore` بوعي — رسالة الرفض
  ثنائية اللغة وتشرح المسار الآمن (فرع جديد ← تحقق ← قرار).
- `--dry-run` يطبع الأمر الدقيق بالسلسلة المقنّعة والحارس يعمل حتى في
  المعاينة.

```bash
STAGE_DIRECT='<سلسلة الاتصال المباشر لفرع التجربة من لوحة Neon>'

npm run db:restore -- --url-env STAGE_DIRECT --file tadmora-YYYYMMDDTHHMMSSZ.dump
npm run db:restore -- --url-env STAGE_DIRECT --file <dump> --dry-run

# الأمر الخام الذي يشغّله السكربت:
pg_restore --no-owner --no-privileges \
  --dbname="$STAGE_DIRECT" tadmora-YYYYMMDDTHHMMSSZ.dump
```

- `--no-owner --no-privileges`: أسماء الأدوار في Neon مُدارة ولا تُنقل مع
  الملف؛ Prisma لا يحتاجها (الاتصال الوحيد من الخلفية — وثيقة 07).
- الملف الناتج (`.dump`) يحمل معه جدول `_prisma_migrations` — أي حالة
  المخطط مطبوعة في النسخة نفسها (التحقق رقم 4 أدناه).

> **r167:** نُفِّذت تجربة محلية كاملة (نسخ → حارس → استعادة → تحقق → ربط
> تطبيق حيّ → تدريب تدوير كلمة المرور) على PostgreSQL محليّ ببيانات البذرة
> — مدخل 1 في
> [docs/runbooks/restore-exercise-log.md](runbooks/restore-exercise-log.md)
> يحمل القيم المقيسة.
> **r183 (2026-10-17): تجربة الإنتاج الفعلية مكتملة** — من قاعدة الإنتاج
> الحيّة إلى قاعدة عزل في نفس مشروع Neon، بتحقق شامل (80 جدولًا
> واحد-لواحد، 124 قيد مفاتيح بلا يتامى) + إقلاع تطبيق production + دخان
> 5/5 شاملًا عزل المؤسستين — المدخل 3 في السجل يحمل كل القيم المقيسة
> والدروس (مطابقة إصدار العميل للخادم، التحقق عبر الاتصال المباشر لا
> الـpooler، وDROP DATABASE WITH (FORCE)).

```text
□ 1. خذ نسخة يدوية بالقالب أعلاه واحفظ الملف خارج جهاز الخدمة
     (تخزين كائنات/قرص خارجي) — النسخة على نفس القاعدة ليست نسخة.
□ 2. أنشئ فرعًا جديدًا في Neon باسم restore-exercise-<تاريخ>.
     متوقع: فرع فارغ بسلسلتي اتصال خاصتين به (pooler + مباشر).
□ 3. استعِد الملف إلى الفرع بالقالب أعلاه.
     متوقع: pg_restore ينتهي بلا أخطاء (التحذيرات المرتبطة بالأدوار
     طبيعية مع --no-owner).
□ 4. تحقق من سلامة الاستعادة بالاستعلامات:
     (r167) البديل المؤتمت: `STAGE_DIRECT="<url>" npm run db:verify
     -- --url-env STAGE_DIRECT` يشغّل الفحوص التالية كاستعلامات حقيقية
     ويطبع حكمًا مقيسًا PASS/WARN/FAIL — أو نفّذها يدويًا:
     psql "$STAGE_DIRECT" -c '\dt'
       متوقع: قائمة جداول المخطط كاملة (~80 جدولًا).
     psql "$STAGE_DIRECT" -c "SELECT migration_name, finished_at
       FROM _prisma_migrations ORDER BY finished_at DESC LIMIT 3;"
       متوقع: آخر ترحيل مطابق لما على الإنتاج.
     psql "$STAGE_DIRECT" -c 'SELECT role, count(*) FROM "User"
       GROUP BY role ORDER BY count(*) DESC;'
       متوقع: توزيع أدوار مطابق للإنتاج تقريبًا (أرقامك أنت).
     psql "$STAGE_DIRECT" -c 'SELECT count(*) FROM "Enrollment";'
       متوقع: عدد قريب من عدّاد لوحة المالك (إحصاءات التسجيلات).
□ 5. اربط التطبيق بالفرع تحققًا حيًا: خذ سلسلة pooler الفرع وضبطها
     في backend/.env محليًا ثم شغّل الخلفية محليًا وافتح
     /api/v1/health ثم صفحة دخول — أو استخدم فحص الدخان مع هدف
     منفصل إن نشرت الفرع كـpreview.
□ 6. تحقق أن الإنتاج لم يُمس (تحقق التراجع):
     - من إعدادات مشروع Vercel: `DATABASE_URL` ما زال يشير لقاعدة
       الإنتاج (لم يتغير أثناء التجربة كلها).
     - نفّذ `npm run smoke` — متوقع: كل الفحوص PASS كما قبل التجربة.
□ 7. نظّف: احذف فرع التجربة من لوحة Neon (Branches → Delete) حتى
     لا تتراكم فروع قراءة على حدود الخطة، واحتفظ بالملف في تخزينك.
```

### 4) أهداف RPO/RTO ومتى تجوز الاستعادة الحيّة (r182 — المرحلة 9)

> «استراتيجية النسخ»: الكوارتز منها وظيفة المالك (Neon) — المنصة تجهّز
> المسار ونقيسه (سكربتات + تجربة محلية مُسجّلة). الأرقام أدناه **أهداف
> معلنة** لوضعَي التشغيل الحاليين، لا نتائج مقيسة بعد:

| الوضع | RPO المستهدف | RTO المستهدف | المسار |
|---|---|---|---|
| المعاينة العامة (الحالي) | ≤ 7 أيام | ≤ 24 ساعة | نسخة يدوية دورية (r166c) + نسخ Neon الذاتية بحسب خطة مشروعك — لا تفترض نافذة معينة دون التحقق من لوحة Neon (Settings/Backups) |
| الطيار المؤسسي (5–10 طلبة) | ≤ 24 ساعة | ≤ 4 ساعات ضمن ساعات العمل | نسخة يومية يدوية قبل يوم الدراسة + Neon PITR إن كانت الخطة تدعمها + تنفيذ قائمة §3 المُجرّبة (مدخل 1 في سجل التجارب) |

**متى تجوز الاستعادة فوق قاعدة الإنتاج الحيّة؟** بترتيب صارم:

1. **لا تُنفَّذ أبدًا** كخطوة تشخيص أو تجربة — التجربة تخصّص فرعًا جديدًا
   (قائمة §3).
2. تجوز فقط كفعل إنقاذ واعٍ بعد: (أ) تعذّر إصلاح البيانات بالمسارات
   العادية، (ب) استعادة على فرع معزول ناجحة ومتحقَّق منها أولًا، (ج) قرار
   المالك الموثّق بتاريخه وسببه، (د) تمرير `--confirm-live-restore` الصريح
   لسكربت `db:restore` (الحارس المزدوج اللغتين يشرح المسار الآمن عند
   الرفض).
3. **التراجع الكودي لا يلمس البيانات أبدًا** (Rollback أعلاه) — التراجعان
   مختلفان عمدًا ولا يُخلط بينهما.
4. بعد أي استعادة حيّة: `npm run smoke` + فحص لوحة المالك قبل إعادة فتح
   الوصول، وتوثيق الحادثة هنا وفي
   `docs/runbooks/restore-exercise-log.md`.

### 5) ما لا يغطيه هذا الدليل

- الجدولة (كل كم مرة؟) والتخزين خارج الموقع مسؤولية المالك — المنصة لا
  تدير دورة نسخ احتياطي داخل التطبيق.

## قيود بيئة النشر (اعرفها قبل أي ميزة جديدة)

- **لا عملية طويلة العمر**: الدوال serverless بلا استماع دائم — الوظائف
  المجدولة تركب cron المنصّة، **ولا WebSocket في المنصة** («الزمن الحقيقي»
  في لوحة المالك استقصاء دوري — وثيقة [03](03-architecture.md)).
- **نظام ملفات زائل لكل استدعاء**: أي ملف يُكتب على القرص المحلي يضيع بانتهاء
  الاستدعاء — لهذا التخزين الدائم للرفعات خلف تجريد التخزين
  (`backend/src/lib/storage.ts`): `STORAGE_DRIVER=postgres` أو `s3`؛ السائق
  المحلي للتطوير المحلي فقط.
- **ميزانية 60 ثانية** للاستدعاء (`maxDuration` في `vercel.json`) — أي مسار
  طويل يجب أن يبقى تحتها.
- **سقف جسم الطلب لوظائف المنصة** (نحو 4.5MB للطلب الواحد): يقيّد الرفع
  المباشر في طلب واحد — عامل حجم الرفعات عند أي توسعة.
- المنصة تضبط `NODE_ENV=production` تلقائيًا (تفعّل كوكي Secure)، والتوقيت
  `UTC` — حواف أيام الحضور تحسب به (وثيقة [03](03-architecture.md)).

## تخزين رفعات PDF في الإنتاج

الوضع الإنتاجي الموثّق: **`STORAGE_DRIVER=postgres`** (r175) — البايتات
تُخزَّن صفوف BYTEA في جدول `BinaryObject` بالمفاتيح القانونية نفسها
(`papers/` و`materials/`)، بوابات الملكية/التسجيل/الإشراف ونطاقات الطلب
وحدود الحجم والحصص كلها كما هي، ولا متغير إضافي مطلوب (السائق يستعمل
`DATABASE_URL` نفسها وترحيل `20261016190858_postgres_binary_objects` يطبَّق
مع الترحيلات). المقايضة بصدق: البايتات داخل قاعدة التطبيق — مناسب لحجم
طيار محدود، وليس معمارية مخزن كائنات؛ راقب حجم الجدول عند التوسّع وخطط
للانتقال إلى `s3`.

تحقق: ارفع ملفًا ثم أعد النشر وافتح الملف مرة أخرى — يُقدَّم من القاعدة.
وبطاقة «تخزين الرفعات (PDF)» في صفحة «النظام والتشغيل» (‏`GET /owner/system`)
تعرض حالة الوصول الفعلية للمخزن (فحص memoized كل 60 ثانية).

للتوسّع إلى تخزين كائنات S3-متوافق (AWS S3 / Cloudflare R2 / MinIO) — خطوات
المالك مرة واحدة:

1. أنشئ حاوية (bucket) — مثل `tadmora-files` — وفعّل الوصول للكائنات فقط
   (لا استضافة عامة: كل تقديم يمر عبر الخلفية المصرَّدة).
2. أنشئ رمز وصول API (Access Key ID + Secret) بصلاحيات على تلك الحاوية
   فقط — لا مفاتيح الحساب كاملة.
3. في إعدادات مشروع Vercel أضف المتغيرات:
   - `STORAGE_DRIVER=s3`
   - `S3_ENDPOINT=https://<ACCOUNT_ID>.r2.cloudflarestorage.com` — انسخه من
     لوحة R2 (عنونة path-style)؛ مع MinIO عنوان خدمتك، ومع AWS S3 إقليمك
     مثل `https://s3.eu-central-1.amazonaws.com`
   - `S3_REGION=auto` (اصطلاح R2؛ إقليمك مع AWS)
   - `S3_BUCKET=tadmora-files`
   - `S3_ACCESS_KEY_ID=…` و`S3_SECRET_ACCESS_KEY=…` (سريّان — بيئة Vercel
     فقط، لا يوضعان في الشيفرة أو `.env.example` بقيم حقيقية)
4. احفظ وأعد النشر، وتفحص السجلات: لا رسالة
   «STORAGE_DRIVER=s3 requires: …» (تعني متغيرًا ناقصًا — `env.ts` يمنع
   الإقلاع أصلاً حتى تكتمل).
5. تحقق: ارفع ورقة بحث من حساب طالب تجريبي ثم افتح الملف — إن كان يعمل
   فالبايتات في الحاوية (تحقق من لوحة الحاوية إن أحببت).

> دليل التحقق الآلي (r167): بروتوكول S3 نفسه يُختبر فعليًا في
> `backend/tests/modules/storage-s3-live.test.ts` — يقلع خادم s3rver حقيقيًا
> في CI (اعتمادية تطوير فقط، لا تُشحن للإنتاج) ويقود السائق عبر المصنع
> الحقيقي: رحلة put/stat/get متطابقة البايتات، `Range` → 206 مع
> `Content-Range`، 404 للمفتاح المفقود، 416 للنطاق غير القابل للتحقيق،
> بقاء `content-type: application/pdf`، ومسبار `probeStorage` — بما في ذلك
> رفض 403 لمفتاح وصول غير مسجّل (فحصها `reachable: false`). الحدّ الصادق:
> s3rver 3.7.1 لا يتحقق من صحة حساب توقيع SigV4 نفسه (يفحص وجود مفتاح
> مسجّل فقط) — صحّة التوقيع تبقى مثبتة بالمتجه الثابت
> `storage-sigv4.test.ts` + الفحص اليدوي أعلاه (الخطوة 5) لدى المالك.

## تشغيل المساعد الذكي بنموذج حقيقي (خطوات المالك — اختيارية)

الافتراضي محلي حتمي (تأليف واعٍ بالإتقان، بلا تكلفة ولا استدعاءات خارجية).
لتشغيل نموذج لغوي حقيقي (أي خدمة متوافقة مع OpenAI: OpenAI نفسها، Groq،
OpenRouter، DeepSeek، Together، vLLM/Ollama ذاتي الاستضافة):

1. أنشئ مفتاح API لدى المزوّد — يُفضَّل مفتاح بميزانية محدودة (الخدمة تحدّد
   الطلب بـ20 طلبًا/دقيقة/مستخدم و800 توكن إخراج للرد الواحد، لكن مسؤولية
   السقف المالي للمفتاح على المالك).
2. اختر اسم النموذج من لوحة المزوّد (مثل `gpt-4o-mini` أو مكافئه الرخيص
   لدى Groq/DeepSeek — ردود دراسيّة قصيرة لا تحتاج نموذجًا ضخمًا).
3. في إعدادات مشروع Vercel أضف:
   - `AI_PROVIDER=openai`
   - `AI_API_KEY=…` (سري — بيئة Vercel فقط، لا يوضع في الشيفرة)
   - `AI_MODEL=…`
   - `AI_BASE_URL` فقط لو المزوّد ليس OpenAI نفسها (مثل
     `https://api.groq.com/openai/v1` أو عنوان خادم vLLM/Ollama)
4. احفظ وأعد النشر. إن ظهرت رسالة «AI_PROVIDER=openai requires: …» فمتغير
   ناقص — `env.ts` يمنع الإقلاع حتى يكتمل.
5. تحقق: افتح صفحة «المساعد الذكيّ» — الشارة تعرض اسم النموذج (والعنوان
   يقول «مدعوم بنموذج لغويّ حقيقيّ»)، ثم اسأل سؤالًا وانتظر الرد. فشل المزوّد
   يظهر خطأً صادقًا مع زر إعادة محاولة — عمدًا لا fallback قالبيًا صامتًا.

## علاقة النشر بالمنظومة

تادمورا لا يعتمد على أي خدمة خارجية وقت التشغيل افتراضيًا (لا بريد، لا
Redis؛ المساعد الذكيّ محلي ما لم يفعّل المالك `AI_PROVIDER=openai` بمزوّد
حقيقي — والتخزين داخل قاعدة Neon ما لم يفعّل `s3`) — قاعدة البيانات هي
الاعتماد الخارجي الوحيد افتراضيًا، مما يجعل النشر قابلًا للتكرار على أي
استضافة Node بنفس المعادلة (بناء + ترحيل + إقلاع).
